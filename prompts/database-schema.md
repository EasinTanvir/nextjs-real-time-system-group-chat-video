# Production Chat Database Schema

## Goal

Create a production-ready PostgreSQL schema and Drizzle migration workflow for the Express backend. The schema must support user profiles, settings, friend-request and friendship flows, direct and group conversations, membership roles, messages, message read receipts, and the indexes and constraints needed by the chat application.

## Architecture Decisions

- Keep all database code inside `server/`; the Next.js frontend will not connect to Postgres directly.
- Use Drizzle ORM with the PostgreSQL `pg` driver and `DATABASE_URL` from `server/.env`.
- Manage the database schema entirely through versioned Drizzle migrations; do not issue unmanaged, ad-hoc DDL against Neon.
- Use `uuid` primary keys generated by PostgreSQL, `timestamptz` timestamps, and `text` enums enforced with PostgreSQL enum types.
- Preserve the existing manual authentication implementation. This work only provides fields that let an existing auth system associate an authenticated identity with a `users` record; it will not add, replace, or modify login/session/token behavior.
- Store exactly one canonical friendship row per user pair, with the lower UUID always stored as `user_one_id`. This prevents duplicate reciprocal friendships.
- Store a canonical pair on a direct conversation (`direct_user_one_id`, `direct_user_two_id`) and make it unique, so concurrent requests cannot create duplicate direct conversations. Direct conversation membership will still be stored in `conversation_members` for uniform authorization queries.
- Messages are immutable text-message records for this initial schema. Attachments, reactions, edits, soft deletion, calls, and notifications are deliberately deferred because they were not requested.

## Schema Design

### Enums

- `friend_request_status`: `pending`, `accepted`, `rejected`, `cancelled`
- `conversation_type`: `direct`, `group`
- `conversation_member_role`: `owner`, `admin`, `member`

### `users`

- `id` UUID primary key
- `email` unique, case-insensitive at the application boundary
- `username` unique, case-insensitive at the application boundary
- `display_name`, `avatar_url`, `bio`
- `last_seen_at`, `created_at`, `updated_at`
- Unique indexes for `email` and `username`; a searchable index for user discovery.

### `user_settings`

- One-to-one relationship with `users` (`user_id` is both primary key and foreign key)
- `theme`, `notifications_enabled`, `read_receipts_enabled`, `created_at`, `updated_at`

### `friend_requests`

- `id` UUID primary key
- `sender_id` and `receiver_id` foreign keys to `users`
- `status`, optional `responded_at`, `created_at`, `updated_at`
- Check constraint prohibiting self-requests
- Partial unique index allowing only one pending request for a sender/receiver pair
- Indexes for received and sent request lists, sorted by newest first

### `friendships`

- `id` UUID primary key
- `user_one_id`, `user_two_id` foreign keys to `users`
- `created_at`, `updated_at`
- Check constraint requiring different users and canonical UUID ordering (`user_one_id < user_two_id`)
- Unique pair constraint, plus per-user lookup indexes

### `conversations`

- `id` UUID primary key
- `type`
- Group-only metadata: `name`, `description`, `avatar_url`
- Direct-only canonical pair: `direct_user_one_id`, `direct_user_two_id`
- `created_by_id` foreign key to `users`
- Denormalized activity fields: `last_message_id` (added after `messages` to avoid a creation cycle) and `last_message_at`
- `created_at`, `updated_at`
- Check constraints enforcing either group metadata or the direct-user pair as appropriate, and disallowing a user from directly conversing with themself
- Unique direct-user-pair constraint and a conversation-list activity index

### `conversation_members`

- Composite primary key: `conversation_id`, `user_id`
- `role`, `joined_at`, optional `last_read_message_id`, `last_read_at`, optional `left_at`
- Foreign keys to `conversations`, `users`, and `messages` where appropriate
- Indexes for a user’s active conversations and a conversation’s active members

### `messages`

- `id` UUID primary key
- `conversation_id`, `sender_id` foreign keys
- Non-empty `content`
- `created_at`, `updated_at`
- Indexes for cursor pagination by `(conversation_id, created_at DESC, id DESC)` and sender lookup
- The service layer will verify sender membership before inserting a message; the schema prevents orphaned references.

### `message_reads`

- Composite primary key: `message_id`, `user_id`
- `read_at`
- Foreign keys to `messages` and `users`
- Index for unread/read-receipt lookup by user and message

## Assumptions

- `DATABASE_URL` is already configured in `server/.env`; its value will not be printed, moved to browser code, or committed.
- The backend currently contains no implementation, ORM, migration configuration, or schema files.
- UUID routes are acceptable even though the existing UI mock data uses a `conv_` example identifier.
- User presence remains an in-memory Socket.IO concern at first; `last_seen_at` is persisted for offline status.
- User identity creation and password/session storage belong to the owner’s existing authentication design and are out of scope.

## Implementation Plan

1. Install the backend-only Drizzle/Postgres dependencies and add schema/migration scripts.
2. Add a reusable database client that fails clearly when `DATABASE_URL` is unavailable and does not log connection strings.
3. Define PostgreSQL enums, tables, foreign keys, check constraints, unique constraints, relations, and indexes in Drizzle.
4. Generate an initial SQL migration from the Drizzle schema.
5. Review the generated SQL to confirm dependency order, all constraints, and all requested indexes.
6. Run safe local checks. Apply the migration to the configured Neon database only if explicitly requested or if it is a normal approved implementation step and the connection target is clearly a development database.

## Security Requirements

- Read `DATABASE_URL` only on the Express server; never use a `NEXT_PUBLIC_` variable for it.
- Never print credentials or include them in code, migrations, logs, prompts, or documentation.
- Enforce foreign keys, canonical relationship pairs, and ownership/membership validation in future backend services.
- Keep authorization in backend services: clients must never supply trusted user IDs, roles, or membership status.
- Use parameterized Drizzle queries rather than string-built SQL in future data access code.

## Acceptance Criteria

- Drizzle is configured in `server/` and reads `DATABASE_URL` from server-only environment configuration.
- A checked-in, reproducible initial migration creates every enum and table described above.
- Each table has appropriate primary keys, timestamps, foreign keys, constraints, and query indexes.
- The schema prevents self friend requests, duplicate pending requests, duplicate reciprocal friendships, and duplicate direct conversations.
- The schema supports direct conversations, group conversations, group roles, message pagination, unread tracking, and per-message read receipts.
- No authentication flows or frontend code are changed.
- No secret is exposed or committed.

## Manual Testing Steps

1. Confirm `server/.env` contains a valid `DATABASE_URL` locally without displaying it.
2. Generate and apply the initial migration to a development Neon branch/database.
3. Verify all enums, tables, foreign keys, and indexes exist using the Drizzle migration output or a database inspector.
4. Attempt a self friend request, a duplicate pending request, a duplicate friendship pair, and a duplicate direct-conversation pair; confirm the database rejects each invalid write.
5. Create a group conversation, add owner/admin/member rows, create messages, and add read receipts; confirm referenced data is returned and deletions respect foreign-key rules.
6. Query a user’s conversations and one conversation’s messages using the intended indexes and cursor ordering.
